## Pass 1: the server trust boundary

Read in full: the 14 non-seed migrations, both Edge Functions, `config.toml`, `web/apagar-conta/app.js`, the
client's `SupabaseClient` and `LedgerService`.

**Not run.** The plan was to probe a local Supabase as a hostile client. Docker isn't running on the PC and this
session can't start it (no sudo, the user isn't in the `docker` group), so every finding here is from reading the
policies and grants. They are simple enough to read with confidence (a `for all` policy plus a `delete` grant leaves
little to interpret), but none has a repro yet.

### The shape of the problem

The server was designed in D70 for "my rows on my project": one login, one owner, trusted. Cadernetas (D104) widened
*who can read* with care: composite foreign keys, membership functions, RLS by caderneta. What was never revisited is
*how much* and *what kind* of writing an account may do, because until the closed test every account was the user's
own. S1, S3 and S4 are the same leftover seen from three sides.

### S1 (A) — Nothing bounds what one account can write, on a project every tester shares

- **Where:** table grants in `20261025000000_catalog.sql:238` (`insert, update, delete` to `authenticated` on every
  catalog table, no length checks on any text or JSON column); `create_ledger` (`20261027000000_ledgers.sql:271`, no
  limit per account, and each call seeds 89 categories and 10 tags); the `receipts` bucket
  (`20261025000000_catalog.sql:294`, created with no `file_size_limit` and no `allowed_mime_types`, so the 50 MiB
  global limit applies).
- **Why it matters now:** sign-up is open with the key that ships in the APK, in a public repo. The project is on the
  free tier: 500 MB of database, 1 GB of storage (`costs.md:43`). One script with one account reaches either in
  minutes: twenty 50 MiB uploads, or a loop of `create_ledger`. A free project over its database quota is put in
  read-only mode, which stops every tester's sync at once.
- **Already seen as single bugs:** T-43 (queue flood, long descriptions). The pattern is wider than that ticket.
  Compare the `contributions` bucket, made a week later with a 2 MiB limit and three MIME types: the newer code knows
  the rule, the older bucket never got it.
- **Fix direction, cheapest first:**
  1. A migration setting `file_size_limit` (about 1 MiB) and `allowed_mime_types` on `receipts`. Check the largest
     page and photo the app has ever uploaded first, so no supported client is refused.
  2. `check (length(...) <= n)` on the free-text columns (`description`, `name`, `label`, `display_name`, `reason`)
     and a size check on `segment` and `payments`. Add as `not valid`, measure existing rows, then validate.
  3. A cap on cadernetas per account inside `create_ledger`, and a row ceiling per caderneta (a trigger on `receipt`
     counting per `ledger_id` is enough; lines and items follow from receipts).
  4. Move to Pro before the open store regardless: with a spend cap it turns "everyone's sync stops" into "a bill
     alert".
- **Checked:** by reading. The read-only behaviour at quota is Supabase's documented one, not tested here.

### S2 (A) — Files outlive the data they belong to; deletion is only as complete as the client's last network call

- **Where:** `delete_ledger`, `drop_member`, `delete_me` (`20261027000000_ledgers.sql:354–433`) delete rows by
  cascade. Storage can't be cleared from SQL, so the phone (`LedgerService.kt:74–101`) and the site
  (`web/apagar-conta/app.js`) list the folder and delete the files *before* calling the function. Nothing on the
  server checks afterwards.
- **How files get left behind:**
  - Another member's phone uploads a page between the list and the function call.
  - The "am I alone?" check and the delete are separate requests; a member joining in between means the leaver
    deletes only their photos, and if that member then leaves the same way the race repeats.
  - `remove_member` on the last other member, then the owner deletes the login from a phone that has been offline:
    the listing runs under whatever the phone knows.
  - A login deleted from the Supabase dashboard cascades `ledger_member` but not `ledger`: the caderneta stays with
    no members, every row and file intact, reachable by nobody.
  - Any object whose row was lost (the reverse of T-28).
- **Why it matters:** the files are the pages, which are the whole purchase history (store, items, prices, payment
  method). The privacy policy and Play's data-safety form promise deletion. An orphaned folder has no member, so no
  client can even list it; only the secret key can, and no tool looks.
- **Fix direction:** make the server responsible. A `storage_purge` table filled by an `after delete` trigger on
  `ledger` (and on `receipt_photo`), drained by a scheduled Edge Function that removes the objects; plus a periodic
  sweep that deletes any top-level folder in `receipts` with no matching `ledger`, and deletes cadernetas with no
  members. The client's delete-first stays as the fast path. This also removes the need for the `own_uploads`
  policy's "delete after leaving" special case.
- **Checked:** by reading. Whether orphans exist online today is one read-only query with the secret key (folders in
  `storage.objects` for `receipts` whose first segment isn't a `ledger.id`); not run, it needs the user's go-ahead.

### S3 (B) — Roles guard the category tree and nothing else

- **Where:** policy `members … for all` on `receipt`, `receipt_line`, `receipt_photo`, `product`, `store_item`,
  `tag`, `product_tag`, `issuer`, `receipt_scan` (`20261027000000_ledgers.sql:157–163`), with `delete` granted;
  storage policy `member_folder … for all` (`:200`).
- **What it allows:** a plain member can hard-delete every receipt and every file of a shared caderneta. The schema's
  own rule is that rows are tombstoned, never deleted (`catalog.sql:5`), and sync pulls by `updated_at`, so a hard
  delete propagates to no one: the server loses the data, the other phones keep showing it, and a new phone gets
  nothing. There is no way back except the nightly dump on the PC.
- **Is it a decision?** D104 says everyone in a caderneta sees everything, which covers reading. It doesn't say a
  member may destroy everything. The app never sends these deletes, so the grant exists only for a modified client
  or a bug.
- **Fix direction:** revoke `delete` from `authenticated` on every synced table the client doesn't delete from. The
  client deletes only `receipt_line` (D164's removed lines) and `receipt_photo` (withdrawal); both could become
  definer functions later. For storage, split `member_folder` into read and insert for members, and delete for the
  uploader or a manager. If "any member may delete anything" is what's wanted, write it into `decisions.md`.
- **Checked:** by reading; client deletes confirmed by grep (`SupabaseRemote.delete`, `PhotoWithdrawal`).

### S4 (B) — Columns the server owns are writable by the client

- **Where:** grants are per table, so every column is the client's to set: `category_source`, `category_confidence`,
  `category_model`, `suggestion_*`, `sold_by_source`, `read_size_*`, `read_model`, `fetched_by`, `created_by`,
  `receipt_scan.user_id`, `user_modified`. The migrations' comments say otherwise ("written only by the server and
  pulled by the phone, never pushed", `20261029000000_system_one_reads.sql:3`); only the app's good manners enforce
  it. T-46 is one case.
- **Why it matters later, not today:** inside one's own caderneta, forging "Jev said so with 0.99" hurts nobody
  else. Stages 9 and 10 (shared curation, analyses across users) are exactly the features that will trust
  provenance. Building them on columns any client can set would be the classic scope-creep hole.
- **Fix direction:** before stage 9, a `before insert or update` trigger that, for role `authenticated`, pins the
  server-owned columns to their old values and sets `created_by`, `fetched_by` and `user_id` from `auth.uid()`.
  Column-level grants would also work but break `Prefer: resolution=merge-duplicates` upserts that name those
  columns, so the trigger is the compatible route.
- **Checked:** by reading.

### S5 (B) — The open endpoints' global caps are themselves the way to switch them off

- **Where:** `feedback_limits` (`20261031000000_feedback_tickets.sql:52`: 30 a day per install, 300 an hour for
  everyone); `contribute/rules.ts` (300 files and 150 MB a day per install, 3,000 files an hour for everyone). Both
  accept callers with no login; install ids are free to invent.
- **What follows:**
  - Holding either global cap full takes one request every 12 seconds (feedback) or about one a second (contribute),
    and every tester's reports or contributions are refused for as long as it lasts. These are the channels the
    closed test depends on.
  - The contribute cap counts files, not bytes: 3,000 files of 2 MiB is about 6 GB an hour into a 1 GB allowance.
  - Feedback at its cap is 300 × 30 KB, about 216 MB a day into the 500 MB database.
  - Both limit checks read a count and then write, so parallel requests pass together.
  - Contributions have no expiry ("kept while the test lasts", with no date and no job).
- **Fix direction:** a global byte budget in `contribute`; a per-IP count in both (the function sees
  `x-forwarded-for`; for feedback that means moving the insert behind a function or a definer RPC); drop feedback's
  body cap to what a crash log needs; a dated purge of contributions. Play Integrity is the real answer and can wait
  for the open store.
- **Checked:** by reading, arithmetic from the constants.

### S6 (A, already on the user's list) — Production is also the development database, and its settings aren't in the repo

- **Where:** `status.md` › "Pending, by the user": debug builds, audits and the tools on the PC all use the online
  project; `.env.local` holds its secret key and database password.
- **Why it's ranked A here:** every other safeguard in this pass assumes that what was tested is what runs. Today a
  debug build with a half-made migration's assumptions writes into the testers' database, and a session holding the
  secret key is one wrong flag away from it. It has been "not now" since 2026-10-31; the closed test is the moment
  it stops being cheap to postpone.
- **Also:** `config.toml` describes only the local stack (passwords of 6 characters, e-mail confirmation off, no
  captcha). What the online project enforces lives in the dashboard and no review has seen it. Worth five minutes:
  e-mail confirmation on, a minimum password length, leaked-password protection, captcha on sign-up, the redirect
  allow-list, the auth rate limits. Then either `supabase config push` from the repo or a short `docs/` page
  recording the values, so the next change is a diff.
- **Checked:** by reading the docs; the online settings can't be seen from here.

### S7 (C) — The effective policies aren't written down anywhere

`20261027000000_ledgers.sql:63–80` drops every policy on fifteen tables by loop and recreates some. The result is
right as far as reading can tell (`audit_log`, `category_rule` and `categorize_job` end with RLS on and no policy,
which is the intent), but no file states the final set and no test pins it. A pgTAP file with `policies_are` and
`table_privs_are` per table would turn the next accidental `grant` into a failing test. S.

### What's sound

- **Isolation between cadernetas.** Composite foreign keys that include `ledger_id` make a cross-caderneta reference
  impossible even for code that bypasses RLS. This is the most important property and it's built into the schema,
  not into policies.
- **Membership changes only through functions**; the tables are read-only to clients. Owner invariants (a caderneta
  keeps an owner; hand over before leaving) are enforced in one place.
- **Definer functions** pin `search_path` and revoke execute from `public`; new tables get no grants by default.
- **Invite codes:** 40 random bits, single use, a week. Guessing one at API speed is not practical.
- **`categorize`:** refuses without the shared secret (an unset secret also refuses); sends item text only.
- **`contribute`:** a closed grammar of names and UUIDs; withdrawal is recorded before anything is deleted.
- **Server releases:** `docs/releases/server.md` with a compatibility note per migration is better practice than
  most teams have.

### Not examined in this pass

The online project's settings; the Edge Functions' behaviour when Jev or Open Food Facts misbehave; `pg_cron` and
Vault setup online; anything requiring the stack to run.

## Pass 2: data ownership and sync

Read in full: `sync/SyncEngine.kt`, `SyncWorker`, `OtherLedgers`, `Ledgers`, `SupabaseRemote`, `LedgerService`,
`data/ReceiptParser.kt`, `AccountSettings`, `LocalCadernetas`, `GetNFApp`, `RestartActivity`; the relevant parts of
`ReceiptStore`, `ReceiptDatabase`, `Backup` and `BackupService`; the two-phone tests in `SyncEngineTest`.

### The shape of the problem

`data-model.md` was approved for a world where "the PC only reads, the phone is the source of truth, the server
never edits, so there are no sync conflicts". Each of those has since been reversed: the server writes (Jev), and
several phones write the same caderneta. Sync grew to match one incident at a time (D104, D164, T-12, T-28, T-29),
and each table ended with the rule its incident needed. The catalog got a proper three-way merge. Receipt lines, the
table that holds the money, did not.

What the sync does today, per table. Nothing in the repo states this in one place; writing it down is what exposed
L1.

| Rows | Who writes | When two phones differ | How a removal travels |
|---|---|---|---|
| category, tag, product, store_item | phones; Jev for some columns | field by field against `sync_base` (D164) | `deleted` flag |
| receipt_line | every phone that reads the page; a person's corrections in the same row | whole row, the last push wins; a dirty local row ignores the pull | explicit delete, then the others notice its absence |
| receipt header | every phone that reads the page | the phone's own reading stands | none: a pull skips `deleted` rows |
| receipt, its photos | the phone that scanned | version counters, not dirty flags | none for receipts; withdrawal for photos |
| issuer, product_tag, link_suggestion | phones | whole row, dirty wins | `deleted` flag on product_tag |

### L1 (A) — A phone that re-reads a receipt overwrites everyone's corrections to its lines

- **Where:** `data/ReceiptParser.kt:104–147` (`write` deletes the receipt's lines and inserts all of them with
  `dirty = true`, carrying over corrections from *this phone's* copy); `sync/SyncEngine.kt:259` (dirty lines go up
  as whole rows); `:103–105` (push runs before pull); `:454` (a dirty line ignores what the pull brings).
- **Scenario:** two phones share a caderneta. On phone A the person fixes a line (its product, or types its
  discount) and A syncs. Phone B hasn't synced since before that. B then re-reads its pages: at start after an app
  update whose parser version changed, or after Room 14 → 15, whose `ReparseSurcharged` forces it
  (`ReceiptDatabase.kt:152`), which is in the next build. B's re-read rebuilds every line from B's stale copy, marks
  them dirty and pushes them. The server now holds B's lines; A pulls them over its own. The correction is gone on
  every phone and on the server, with no error anywhere.
- **Reach:** any caderneta with two phones, including one person with two devices. The window is as long as B stays
  unsynced, which for a phone that isn't opened is days. Every parser fix shipped (T-37 to T-40 are queued) triggers
  it for every receipt.
- **Evidence — reproduced:** `SyncEngineTest.aStalePhonesReReadMustNotUndoAnotherPhonesLineCorrection` (added with
  this review, `@Ignore`d so the suite stays green). Un-ignored it fails:
  `the server still has A's product for the line expected:<ca64cae1-…> but was:<null>`. Run with
  `./gradlew :app:testDebugUnitTest --tests '*SyncEngineTest.aStalePhonesReRead*'` after removing the `@Ignore`.
- **Fix direction:** two steps, the first small.
  1. In `ReceiptParser.write`, mark a line dirty only when what it wrote differs from what was there. A re-read that
     changes nothing then pushes nothing. This also ends the churn in L2.
  2. Give lines the catalog's merge: a `sync_base` per line, push only changed fields, and a pull into a dirty line
     keeps the phone's changed fields and takes the rest. The extracted columns and the correction columns
     (`product_override_id`, `discount_*`) then stop travelling together.
- **Fixed when:** the test passes un-ignored, and its mirror (B corrects, A re-reads) too.

### L2 (B) — Lines are both derived on every phone and synced as data

- **What happens:** a receipt adopted from the server arrives with its page; `SyncWorker.kt:66` then has this phone
  read the page and push the result. With N phones a receipt is read N times and its lines written to the server N
  times, each write stamping `updated_at`, each making every other phone pull the lines again. A parser bump repeats
  that for every receipt on every phone.
- **Why it's a design question, not only waste:** the page is declared the source of a receipt's data
  (`architecture.md`), so lines are a cache of `parse(page)`. A cache that is also synced has two sources of truth,
  and phones on different app versions hold different parsers: the lines on the server are whatever parser touched
  them last, which can be the older one. L1 is this, plus corrections riding in the same rows.
- **Options:** (a) keep syncing lines but treat extracted columns as write-once per parser version (a phone pushes
  them only if its parser is newer than the server's `parser_version` for that receipt); or (b) sync only the page
  and the corrections, and let each phone derive. (a) is the smaller change and keeps the server queryable for Jev
  and for stage 10.
- **Checked:** by reading.

### L3 (B) — A database file doesn't know which caderneta it belongs to

- **Where:** the pairing of local files and caderneta lives outside the data: preferences `ledger` and
  `legacy_ledger` plus a file-name convention (`AccountSettings.kt:22,73–93`). `SyncEngine.sync(remote)` pushes
  whatever database it was built on into whatever caderneta `remote` names. A backup's manifest has no caderneta id
  (`Backup.kt:18`), and a restore swaps in the database with its cursors, bases and "already uploaded" marks.
- **What rests on it:** T-16 (a restore into another caderneta never uploads; open) is the known case. The app
  singletons are also bound to one caderneta at first use (`GetNFApp.kt:24–40`) while `SyncWorker.kt:47` reads the
  open caderneta fresh from preferences; today the two can't disagree for longer than it takes `exitProcess` to run
  (`Cadernetas.kt:76–77`), so this is sound by timing rather than by construction. The cost of being wrong is the
  worst the app can do: one caderneta's receipts pushed into another's members' view.
- **Fix direction:** write the caderneta's id into `sync_state` at the first sync and have `SyncEngine.sync` refuse
  a `remote` with another id. Put the id in the backup manifest; a restore into a different caderneta clears the
  sync state (cursors, bases, uploaded marks) so everything goes up as new, which is T-16's fix. About thirty lines,
  and it turns three separate "can't happen" arguments into one check.
- **Checked:** by reading; T-16's repro already exists (`reviewRound2RestoredCleanDatabaseMustUploadToNewLedger`).

### L4 (B) — Removal has four mechanisms, and receipts have none

- Catalog rows carry a `deleted` flag. Lines are deleted for real and the other phones infer it from absence
  (`reconcileLines`, with its own durable queue since T-12). Leaving or deleting a caderneta cascades on the server
  and leaves the phone's files in place (`status.md` › Open items). Photos have withdrawal. A receipt can't be
  removed at all: no screen (T-50), and `applyReceipts` skips a row marked `deleted` rather than acting on it
  (`SyncEngine.kt:532`).
- **Why now:** T-50 will be built soon because testers will scan wrong receipts. Built the way the others were, it
  becomes a fifth mechanism. It also has to reach Storage (the page and photos), which is S2 again. Decide the rule
  once: a `deleted` flag on the receipt that every phone honours by removing its local copy, and the server-side
  purge from S2 removing the files.
- **Checked:** by reading.

### L5 (C) — The pull cursor assumes nothing on the server takes more than a minute to commit

Pulls ask for rows with `updated_at` later than the last one seen, less 60 seconds (`SyncEngine.kt:354`), and
`updated_at` is stamped when the row is written, not when its transaction commits. A phone's own requests commit in
milliseconds. A maintenance job that updates synced rows inside one long transaction (a backfill migration,
`tools/blank-buyers.py`, a restore) can commit rows whose stamps are already older than every phone's cursor, and
no phone ever pulls them. Rule to adopt: such jobs commit in small batches, or touch the rows again at the end. One
line in `docs/rollout.md` is enough for now.

### L6 (C) — The page's storage path is taken from the row

`applyReceipts` downloads whatever `page_path` the row holds (`SyncEngine.kt:534–547`). The path is always
`<caderneta>/<chave>/page.html` (`:277`), so the phone can compute it and use the column only as "there is a page".
Storage's policy already limits a download to the person's own cadernetas, so the exposure is small (a member
pointing a shared receipt at a page in another caderneta the victim also belongs to); the fix is one line.

### L7 (C) — Three ways to say "this changed"

Receipts use version counters (`version`, `uploadedVersion`), most tables a `dirty` flag, the catalog a `dirty`
flag plus `sync_base`. All three work and are tested. The cost is that each new table picks one by imitation, and a
reviewer has to hold all three to reason about a run. The table at the top of this pass, kept in
`docs/architecture.md` and updated with every sync change, is the cheap remedy; consolidating the mechanisms is not
worth doing before the open store.

### What's sound

- **A phone only syncs a caderneta its login belongs to** (`SyncWorker.kt:59–60`). Another person signing in on the
  same phone can't push the phone's data into their account: the open caderneta isn't theirs, so nothing syncs until
  they open one of their own. (The 11-09 review listed this as not examined.)
- **Ids derived from codes**, so two phones reading the same item offline make the same rows.
- **Pushes are idempotent and a row is cleaned only if it's still what was pushed**; a refused row is parked, not
  retried forever.
- **The parser refuses a page that states another chave** (`ReceiptParser.kt:77`).
- **The catalog's field merge** is the right design; L1 is about extending it, not replacing it.
- **Works with no account**; the server is a copy. That original property survived every later stage.

### Not examined in this pass

The Room migrations one by one against the exported schemas; `CatalogEditor`'s own transactions; the capture
session recovery at start; `ReceiptCopier` between cadernetas beyond its interface.

## Pass 3: what still depends on the PC

Read: `tools/supabase-backup.py`, the systemd units, `supabase-restore-drill.sh`, the headers of `llm-worker.py`,
`load-lexicon.py`, `blank-buyers.py`; `docs/costs.md`. Checked on the PC, read-only: the backup timer is active and
the newest dump is 12 hours old (`supabase-backup.py --check`); the system disk is LUKS-encrypted.

### The shape of the problem

The project began with the phone as a capture device and the data on the PC. Most of that is gone, and gone
properly: nothing a tester does needs the PC to be on. Categorization runs on Supabase's own cron, the site is
static, the app works offline. If the PC died tonight no user would notice. What remains on the PC is everything
*behind* the product: the only backup, every production credential, every deploy.

### P1 (A) — The only backup of every tester's data is a nightly job on a home PC

- **Where:** `tools/supabase-backup.py`, `tools/systemd/getnf-backup.*`. The free tier has no backups of its own
  (`costs.md:59`).
- **What's right:** it works, it retries, it tells the desktop when it gives up, a restore drill exists, and the
  disk is encrypted. For one person's receipts this was a good setup.
- **What changed:** the dump now holds other people's purchase histories and `auth.users` (e-mail addresses and
  password hashes), on a personal machine, in a directory nothing prunes:
  - Files deleted online stay in the mirror forever (the script's own header says so), and 14 dumps are kept. An
    account deleted today is on the PC for at least two weeks in the dumps and indefinitely in `files/`. The
    privacy policy has to say this or the mirror has to honour deletions; pass 4 checks which.
  - The backup's health is one desktop notification on one PC. A week away from the desk is a week unprotected,
    unnoticed.
  - The drill proves a dump loads into an empty local database. Restoring *one person's* data into the live
    project, the case a tester will actually cause, has never been tried and has no tool.
- **Fix direction:** Pro (already the answer to S1) brings seven days of managed backups; the PC job then becomes
  the second copy rather than the only one. Either way, make the mirror delete what is gone online after a grace
  period, and write down in `docs/rollout.md` how a single caderneta would be restored.
- **Checked:** by reading; timer and dump age checked on the PC.

### P2 (A, with S6) — One file holds every production credential, and every session reads it

- **Where:** `.env.local` at the repo root: the database password, the secret key, the Jev key, the categorize
  secret. `CLAUDE.md` tells every worktree session to use the main checkout's copy; the tools find it by walking up
  from their own path.
- **Why it matters:** this is S6 from the other side. An agent session asked to fix a layout bug holds superuser
  access to the testers' database, and tools like `load-lexicon.py` and `blank-buyers.py` default to the online
  project unless told `--local`. Nothing has gone wrong; nothing would stop it.
- **Still open from 2026-10-27:** the database password that reached the systemd journal hasn't been rotated
  (`status.md` › Pending). It is two weeks old now.
- **Fix direction:** with the development project (S6), `.env.local` in the repo points at development only.
  Production credentials move to `~/.config/getnf/` beside the upload key, read only by the four tools that need
  them (backup, tickets, contributions, release), and those tools require an explicit `--online`. Rotate the
  password when doing so.
- **Checked:** by reading.

### P3 (C) — Rules that run in production but live outside git

- **The lexicon** that every caderneta's categorization uses is loaded by hand from
  `test-media/categorize/lexicon-pure.tsv`, a gitignored file (it's built from real receipts). The table is in the
  nightly dump, so it isn't lost, but a change to it has no history and no review. A sanitized copy in the repo,
  loaded by migration like the taxonomy, would fix that.
- **The buyer redaction** exists twice by hand: `BuyerRedaction.kt` on the phone and the same patterns in
  `tools/blank-buyers.py`. T-30 had to be fixed in both. One shared fixture file that both test against would keep
  them from drifting.

### P4 (C) — The LLM worker's remains
