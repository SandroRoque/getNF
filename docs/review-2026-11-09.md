# Review of Caderneta (getNF), 2026-11-09

Base commit `fcc3396` (main, with D171–D176). Started 2026-11-09, finished 2026-11-10; the file and the repro folder
keep the starting date. Nothing in production code was changed, nothing committed or pushed, no request went to SEFAZ,
nothing was written to the online Supabase (tickets were read with `tools/tickets.py list` only). Repros are in
[review-repros/2026-11-09/](review-repros/2026-11-09/), by area. The Kotlin tests there are compiled into the app's JVM
tests for one run by `repro.init.gradle` (its header has the command); each one fails while its defect exists, with a
message that states the expected behaviour. The `.txt` next to each holds the command and output.

## Summary

Filed on 2026-11-10 as tickets T-28–T-49 (one per fix; P3-4 and P3-5 share T-48), with a note on T-6.

1. **A plain member of a shared caderneta can stop their own sync for good, and so can a missing page file.**
   `SyncEngine.pushEvents` doesn't catch the server refusing a member's category edit, and the worker treats any 400
   during a sync as a dead session and signs the person out, so a page object Storage doesn't have means sign-out on
   every run. Shared cadernetas, which the closed test exists to try, are where this happens.
2. **The buyer's name and address survive redaction in the pages the app actually saves** (the WebView's DOM), and the
   photo blanking leaves several lines it read correctly (the buyer's wrapped name and address, a bare CPF, card numbers
   in groups, a named customer and phone). Both reach other members and the test's contributions. The consent text says
   "a página, sem quem comprou".
3. **Numbers:** hand-typed discounts can add up to less than the receipt's; a photo-read discount is added on top of a
   typed one beyond the receipt's; a category parent cycle (two phones, or the server's own taxonomy sync) hangs Início
   and Gastos for every member.
4. **Leaving the demo at the wrong moment can replace the person's own database with the demo's** and then delete the
   original.

Overall: the core (parser, money arithmetic, server functions, RLS) is careful and well tested, and the fixes of
D171–D176 hold. What's left is concentrated where several people and several phones meet, where nobody has tested
yet. I'd fix items 1–4 before recruiting more testers into shared cadernetas.

**Count: 8 P1, 9 P2, 5 P3** (22 findings), plus one design critique shown with numbers. 19 of them reproduced by a test
or script I ran; the rest confirmed by reading.

## Findings

Paths under `android/…/getnf/` are shortened to the package-relative path.

### P1-1 (T-28) — Any 400 during a sync signs the person out; a missing page object does it on every run

- **Where:** `sync/SyncWorker.kt:74` (`if (e.status == 400 || e.status == 401) signOut()` around the whole run);
  `sync/SyncEngine.kt:517` and `:528` (`remote.download(pagePath, …)` unguarded); `sync/SupabaseClient.kt` download.
- **Scenario:** a receipt row names a `page_path` whose object isn't in Storage (an upload that stopped between the row
  and the object, a withdrawal, a hand repair). Supabase Storage answers a missing object with **HTTP 400**
  (`{"statusCode":"404","error":"not_found"}`). The download throws `SupabaseException(400)` out of `sync()`; the worker
  takes it for an expired refresh token and signs the person out. They sign in, the next sync hits the same row, and
  they're out again. Nothing after that row is ever pulled. The same catch turns any other 400 that escapes the engine
  into a sign-out.
- **Evidence — reproduced:** `sync/Review1109SyncWedgeTest.aReceiptWhosePageObjectIsMissingMustNotStopEverySync`
  (statuses thrown per run `[400, 400]`, nothing pulled); Storage's 400 for a missing object checked on the local stack
  (`sync/Review1109SyncWedgeTest.txt`). How often a row loses its object in practice: not measured.
- **Fix direction:** sign out only when `refresh()` itself is refused; inside the run, a failed download skips that
  receipt (adopt it without a page, retry later) and goes on.
- **Fixed when:** the test passes; a run with one bad object pulls everything else and keeps the session.

### P1-2 (T-29) — A plain member's category edit makes every later sync fail at the same step

- **Where:** `sync/SyncEngine.kt:279–285` (`pushEvents`: one upsert, no catch, no parking); server policy
  `managers_log` on `category_event` (`supabase/migrations/20261027000000_ledgers.sql:176`); the category editor
  (`ui/catalog/CategoriesScreen.kt`, `data/CatalogEditor.kt`) never checks the role.
- **Scenario:** in a shared caderneta, a member (not manager) renames or moves a category on the phone, which the app
  allows. The category row itself is refused and parked (D145), but the tree event goes through `pushEvents`, the
  server answers 403 (RLS, 42501), and the exception ends the run before anything is pulled. Every later run stops
  there too. That member's new receipts never go up and other members' changes never arrive; "Sincronizado" stops
  advancing with no message saying why.
- **Evidence — reproduced:** `sync/Review1109SyncWedgeTest.aPlainMembersTreeEditMustNotStopEverySync` (JVM) and
  `sync/member-category-event-refused.sql` (local Postgres: the member's insert is refused with 42501).
- **Fix direction:** hide or disable tree edits for members (the server already decides they can't), and park a refused
  event like a refused row instead of failing the run.
- **Fixed when:** both the test and a member-role UI check pass; a refused event shows in "Não sincronizado".

  are saved, synced to every member of the caderneta and sent with the test's contributions. D104, the policy and the

- **Evidence — reproduced:** `privacy/Review1109PrivacyBuyerRedactionTest` on the repo's own WebView-DOM fixture with a

  form and blank its following list; add the enhanced shape to `BuyerRedactionTest`. Re-run `tools/blank-buyers.py`

- **Fixed when:** the test passes for both shapes, and for RJ's wording.

### P1-4 (T-31) — Photo blanking leaves lines it read correctly: the buyer's wrapped name and address, a bare CPF, grouped card numbers, a named customer

- **Evidence — reproduced:** `privacy/Review1109PrivacySensitiveTextTest` (5 tests, synthetic OCR lines; output in

- **Fix direction:** blank the consumer block to its end (until the next known section: "Tributos", "Protocolo"), add
  the patterns above, and keep a fixture of synthetic slips per pattern.
- **Fixed when:** the five tests pass and `SensitiveTextTest.realFramesLeaks` (local media) shows no regression.

### P1-5 (T-32) — A category parent cycle hangs the reports for every member; two phones, or the server's own taxonomy sync, can make one

- **Where:** every parent walk lacks a visited set: `data/Spending.kt:132` (`ancestry`), `ui/catalog/Pickers.kt:81,119`,
  `data/CatalogEditor.kt:433`, `data/LocalCadernetas.kt:63`. No constraint or trigger on `category.parent_id`.
  `sync_taxonomy_for` (server) moves seed rows without checking.
- **Scenario A:** two managers, not yet synced: one moves "Bebidas" under "Mercado", the other "Mercado" under
  "Bebidas". Each passes its own phone's check; parents merge by field (D164); both land. **Scenario B:** the owner
  moves seed X under seed Y (an ordinary edit); a later taxonomy migration puts Y under X; the next `sync_taxonomy`
  writes the cycle itself. Início and Gastos compute `Spending.slices` in composition for every line: the app hangs
  at start for every member until the row is repaired online.
- **Evidence — reproduced:** the hang, `money/Review1109MoneyTest.aCategoryCycleMustNotHangTheReports`; scenario B on
  the local Postgres, `server/02_queue_flood_and_seed_cycle.sql` (checks B1, B2: the cycle written by the server).
  Scenario A confirmed by reading (`sync/SyncEngine.kt:455–469` applies whatever parents arrive).
- **Fix direction:** cycle-safe walks everywhere (a visited set); a trigger refusing a parent that descends from the
  row; `sync_taxonomy_for` skipping a seed move that would close a cycle.
- **Fixed when:** the test passes; the SQL repro's second move is refused.

### P1-6 (T-33) — Typing a discount on every line can drop part of the receipt's discount

- **Where:** `data/CatalogEditor.kt:319–326` (`setDiscount`), `parse/Derive.kt:92–110`.
- **Scenario:** D174 caps a typed discount from above only. Once no prorated line is left to take the rest, the typed
  ones can add up to less than the receipt's discount. A one-line receipt with R$ 5,00 off: typing 0,00 makes it count
  R$ 5,00 more than was paid.
- **Evidence — reproduced:** `money/Review1109MoneyTest.handTypedDiscountsOnEveryLineMustStillAddUpToTheReceipts`
  (`expected:<50> but was:<0>`).
- **Fix direction:** when an edit leaves no open line, require the remainder exactly (the sheet says "Falta R$ …"), or
  keep an explicit unassigned discount that spending still subtracts.
- **Fixed when:** after any sequence of accepted edits, the lines' net equals `paidCents`.

### P1-7 (T-34) — A photo-read discount is added on top of a hand-typed one, beyond the receipt's discount

- **Where:** `data/PhotoDiscountReader.kt:36–37,66–77` (keeps `manual` lines as known, writes the photo readings);
  `discounts/PhotoDiscounts.kt` judges the photo readings alone.
- **Scenario:** a receipt with R$ 0,50 off. The person types R$ 0,40 on line 1 (allowed by D174), then taps "Descontos:
  ler das fotos". The photo shows R$ 0,30 on line 2; the verdict (photos alone, 0,30 ≤ 0,50) is PARTIAL, so it's
  applied: the lines carry R$ 0,70 and spending is R$ 0,20 low. D174 left photo sums to the reader; this is the reader
  and a typed value together.
- **Evidence — reproduced:** `capture/Review1109CapturePhotoDiscountTest` (`got 70 cents … line 1: 40 manual, line 2: 30
  photo`).
- **Fix direction:** include typed discounts in the verdict's sum; refuse (or ask) when photo + typed exceed the
  receipt's.
- **Fixed when:** the test passes.

### P1-8 (T-35) — Interrupting the demo's start can swap the demo into the person's own caderneta and delete the original

- **Where:** `data/Demo.kt:19–31` (the demo's restore is marked READY, *then* `demo = true` is written);
  `Navigation.kt:94` (`scope.launch` in the composition's scope); `GetNFApp.kt:99–107` (the next start builds the
  restore for whichever caderneta `demo` says, applies it, and `cleanUp()` deletes `restore/previous`);
  `data/Backup.kt:125–161` (`READY` doesn't record which files it was staged for).
- **Scenario:** a new person taps "Ver um exemplo" and, while the bundled demo is extracted, rotates the phone or
  presses Back. The composition's scope is cancelled; the blocking extraction finishes and marks READY, then
  `withContext` throws on return and `demo = true` is never written. At the next start (the person's, or a background
  worker's) the user's own database and receipts go to `restore/previous`, the demo's take their place, and
  `cleanUp()` deletes `previous`. If signed in, the next sync pushes the made-up household into their caderneta. The
  same happens if the process dies in that window.
- **Evidence:** the swap and deletion are **reproduced** at the `PendingRestore` level
  (`localdb/Review1109LocaldbRestoreTest.aRestoreStagedForTheDemoIsNotAppliedToTheUsersCaderneta`); the cancellation
  path is **confirmed by reading**. Not driven on the emulator (it would wipe the emulator's data).
- **Fix direction:** write the target into the READY marker (database path) and refuse to apply it elsewhere; set
  `demo = true` before `markReady()`; launch the demo's start outside the composition (application scope).
- **Fixed when:** the test passes; a start with a READY for another target leaves the user's files alone.

### P2-1 (T-36) — A restored database that can't open crash-loops the app, with the original out of reach

- **Where:** `data/Backup.kt:68–74` (`inspect` checks the manifest and hashes; the database itself is never opened);
  `data/Backup.kt:134–161`, `GetNFApp.kt:99–107`.
- **Scenario:** an archive whose database entry isn't a valid SQLite file of a supported version (exported from a
  damaged phone; hashes match, they're computed at export). Restore stages and swaps it; Room throws at start;
  `cleanUp()` is never reached, but the next start doesn't roll back either (READY is gone). The app crashes at every
  start; the original sits in `restore/previous` where only "clear data", which deletes it too, gets past.
- **Evidence — reproduced:** `localdb/Review1109LocaldbRestoreTest.aBackupWhoseDatabaseIsNotADatabaseIsRefusedBeforeAnythingChanges`
  and `…aRestoredDatabaseThatFailsToOpenIsRolledBackOnTheNextStart`.
- **Fix direction:** in `inspect`, open the staged database read-only (header, `PRAGMA user_version`,
  `integrity_check`); at start, if `previous` exists and the live database fails to open, move `previous` back.

### P2-3 (T-38) — Store codes with letters or dashes lose their non-digits, so different products merge

- **Where:** `parse/NfcePage.kt` `parseItems` (`DIGITS.find(...)` keeps the first run of digits); `data/ReceiptParser.kt:115`.

### P2-5 (T-40) — A page with a repeated item number throws out of the parser, at every start

- **Where:** `data/ReceiptParser.kt:66–82` (the try covers reading, not `write`); `GetNFApp.kt` startup
  `MainScope().launch` and `PageScreen`'s launch don't catch it.
- **Scenario:** a malformed or oddly serialised page repeats an `nItem`; `insertLines` hits the primary key; the

### P2-6 (T-41) — A prorated discount can be larger than the line it lands on

## Follow-up, 2026-11-10: what the stopped reviewers were doing

The area reviewers ran out of usage before reporting. Their transcripts keep no reasoning, only what they ran, so
their unfinished leads were recovered from the commands and outputs and followed up here.

- **Found: the app can't delete a receipt.** `docs/data-model.md` › "6. Exclusões" describes deleting one (with its
  lines, photos and page, on the phone and the server), but no screen or store method does it
  (`ui/`, `data/ReceiptStore.kt`, `data/Catalog.kt`). A tester who scans the wrong receipt, or a test receipt, keeps it
  in every total. Product gap, and a doc that would mislead the next session. Ticket T-50.
- **Held: a member can't write into another caderneta's Storage folder with an encoded `..`.** Storage normalises
  keys (`a/%2e%2e/x.txt` is stored as `x.txt`), but `member_folder` is checked on the normalised name: three attempts
  were refused (400) and nothing landed (`server/03_storage_dotdot.sh`, output beside it; throwaway users, removed).
- **Held: no secret in git history.** The history search's hits were the earlier audit's own scanner pattern and its
  prose; no credential files or tokens are tracked.
- **Held: tester input in the tools.** `contribute` only accepts UUIDs and three fixed file names, so
  `tools/contributions.py fetch` can't be steered outside `test-media/contributions/`; it writes atomically (`.part`
  then rename). `tools/dashboard.html` builds its page with DOM calls and `textContent`, not raw HTML.
- **Seen, already known:** the nightly backup failed on DNS on 2026-11-06, -07 and -09 and recovered by retry (D168's
  design). The dumps and `files/` in `~/getnf-backups` are world-readable (`drwxr-xr-x`, `-rw-r--r--`), but the home
  directory is `drwx------` and there's one user account, so nothing else on the PC reaches them; `chmod 700` would
  keep it so if either changes. Not a finding.
- **Seen, already known:** the server's NOT NULL columns that partial upserts trip over (T-15) were listed again; no new
  case.

- **Money:** compute reports off the main thread and precompute each line's period once (`Spending.total`/`linesIn`

- **Parser warnings in Portuguese,** and a receipt whose arithmetic doesn't close marked in Gastos ("1 nota não
  confere"), not only on its own screen. S.

## Design critiques

The D79 critique is ticket T-49 (an idea).

- **D79 (IPCI, "compared with its own previous price, however long ago; weighted by the month's spending").** Each
  link is weighted by the current month only, so buying a lot on a promotion and little at the old price ratchets the
  level: four products at R$ 10,00, one at R$ 5,00 for a month (ten bought), then back. Every price ends where it began,
  but the level goes 100 → 64,8 → 77,1 (`money/Review1109MoneyTest.aPriceThatComesBackMustBringTheIndexBack`), and "em
  12 meses" is read off that chain. A month's reading also mixes one-month and ten-month comparisons under one month's
  name. Alternative: Törnqvist weights (the mean of both periods' shares), and links scaled to a monthly rate, or the
  12-month figure computed directly from products bought in both end months.
- **D104/D164 (field merge, tree edits by managers).** Field-level merge is right for names and sizes, but a parent is
  a structural field: merging two parents independently is how P1-5's cycle forms. Alternative: validate structure
  at the server (trigger), and on a refusal pull and let the person redo the move.
- **D47 (restore by swapping files at start).** A swap whose target isn't recorded and that only cleans up after the
  database opens leaves two paths to loss (P1-8, P2-1). Alternative: record the target and the previous location in
  the marker, and roll back automatically when the restored database doesn't open.
- **D98/D171 (blanking by recognised text).** Accepting partial OCR as best effort is a reasonable trade, but the rules
  for lines read correctly should be complete for what a DANFE prints. Alternative: blank whole sections by their
  headings (consumer, payment slip) rather than line patterns.
